# Обзор скрапера Яндекс.Маркета (`yandex_market.py`)

Этот документ объясняет «на пальцах», что делает файл
`backend/app/scrapers/yandex_market.py`: какая у него задача, как устроен
пайплайн и какие технологии используются. Читать можно без знания проекта — все
термины объясняются по ходу.

Если вы уже читали [обзор скрапера Wildberries](wb-scraper-overview.md) —
полезно держать его в голове: задача та же, но **подход принципиально другой**, и
ниже видно, почему.

---

## 1. Что вообще делает этот файл

Коротко: **по текстовому запросу пользователя он находит товары на
Яндекс.Маркете и возвращает список карточек** (название, цена, картинка, ссылка,
рейтинг, характеристики).

Пример. Пользователь ввёл «офисное кресло» и регион «Москва». Скрапер откроет
страницы поиска Яндекс.Маркета, вычитает оттуда товары, отсеет мусор и дубликаты,
дополнит карточки деталями и вернёт результат в едином формате приложения.

> **Скрапер** (от англ. *to scrape* — «соскрести») — программа, которая
> автоматически достаёт данные с чужого сайта или сервиса.

---

## 2. Главная идея простыми словами

У скрапера товаров есть два пути добычи данных:

1. **Внутренний API** — «труба» с готовыми данными в формате JSON. Так устроен
   скрапер Wildberries: один запрос — и готовый список.
2. **Парсинг HTML-страниц** — программа скачивает ту же веб-страницу, что видит
   человек в браузере, и «выковыривает» из её разметки нужные куски.

У Яндекс.Маркета **нет удобного открытого API** — поэтому `yandex_market.py` идёт
по **второму пути**: качает HTML страниц поиска и разбирает их. Это сложнее, чем у
WB, и отсюда вытекают все особенности файла:

- надо **листать страницы** (пагинация), а не получить всё за один запрос;
- из «грязной» вёрстки надо аккуратно достать поля → много работы с текстом и
  регулярными выражениями;
- в выдаче много **мусора** (чехлы, плёнки, кабели) и **дубликатов** — их надо
  отфильтровать;
- описание товара на странице поиска скудное, поэтому есть **второй заход** —
  обогащение: открыть карточку каждого товара и дочитать детали;
- если Яндекс заблокирует обычные запросы (капча), есть **запасной план** —
  настоящий браузер (Playwright).

> **HTML** — язык разметки веб-страниц. Браузер по нему рисует картинку, а
> скрапер читает его как текст и ищет нужные теги.
>
> **API / JSON** — машинное «окошко выдачи» и формат данных в нём. У Маркета его,
> по сути, для нас нет — отсюда вся возня с HTML.

## 3. Что используется (технологии и зависимости)

| Инструмент | Зачем он нужен |
|------------|----------------|
| **`curl_cffi`** | HTTP-клиент, который **притворяется браузером Chrome** на уровне сетевого «отпечатка». Основной способ скачать страницы. |
| **`selectolax`** | Быстрый парсер HTML. По CSS-селекторам находит нужные элементы на странице (`HTMLParser`, `.css(...)`). |
| **`re` (регулярные выражения)** | Достаёт числа и куски текста из «человеческих» строк: цену, рейтинг, число отзывов. |
| **`difflib.SequenceMatcher`** | Сравнивает названия «на похожесть», чтобы ловить дубликаты, отличающиеся парой символов. |
| **`ThreadPoolExecutor`** | Запускает обогащение карточек **в несколько потоков параллельно** (по 4 за раз). |
| **`Playwright`** | Запасной вариант: настоящий браузер Chromium, если `curl_cffi` упёрся в капчу. |
| **Redis** (`app/core/cache.py`) | Кэш «запрос → результат», чтобы не дёргать Маркет повторно. |
| **`app/core/regions.py`** | Справочник регионов: даёт `yandex_market_id`, который выставляется куки `yandex_gid`. |
| **`app/core/config.py`** (`settings`) | Настройки: число страниц, вкл/выкл кэш, таймауты. |

> **TLS-отпечаток (JA3/JA4)** — по тому, *как именно* программа устанавливает
> защищённое соединение, сервер отличает настоящий браузер от скрипта. Обычные
> Python-библиотеки выдают себя; `curl_cffi` с `impersonate="chrome120"`
> подделывает отпечаток под Chrome.
>
> **CSS-селектор** — способ указать элемент на странице, например
> `[data-auto="snippet-title"]` — «элемент с атрибутом `data-auto`, равным
> `snippet-title`». Маркет помечает важные блоки такими `data-auto`-метками, и
> скрапер цепляется именно за них.

## 4. Пайплайн: что происходит шаг за шагом

Точка входа — метод `YandexMarketScraper.search(request)` (строки ~600–633).
Главная особенность: **две попытки добычи** — сначала лёгкая (`curl_cffi`), при
неудаче — тяжёлая (Playwright).

```
Запрос: { query: "офисное кресло", region: "moscow" }
        │
        ▼
1. Нормализуем запрос, определяем регион (пустой запрос → пустой результат)
        │
        ▼
2. Есть в кэше Redis? ── да ──► возвращаем сохранённый результат
        │ нет
        ▼
3. ПОПЫТКА 1 — curl_cffi (_fetch_products_sync):
     • открываем сессию, ставим куку региона, заходим на главную (разогрев)
     • листаем страницы поиска (пагинация)
     • парсим HTML каждой страницы → товары
     • отсеиваем мусор и дубликаты
     • обогащаем карточки (параллельно)
        │
        ├── получили товары? ── да ──► кэшируем и возвращаем
        │ нет / ошибка / капча
        ▼
4. ПОПЫТКА 2 — Playwright (_fetch_with_playwright):
     • запускаем настоящий Chromium
     • те же страницы, тот же парсинг и обогащение
        │
        ├── получили товары? ── да ──► кэшируем и возвращаем
        │ нет
        ▼
5. Возвращаем пустой список + понятную ошибку
```

Дальше — про каждый нетривиальный шаг.

### Шаг 2. Кэш (Redis)

Ключ — регион + запрос: `ym:search:moscow:офисное кресло` (`_cache_key`). При
попадании в кэш мы мгновенно отдаём сохранённый результат и **не ходим в сеть**.
Записи живут по `cache_ttl_seconds` (6 часов). Если Redis недоступен — кэш молча
отключается, приложение не падает.

### Шаг 3. Разогрев и регион

Перед поиском (`_fetch_products_sync`) скрапер:

1. Создаёт сессию `curl_cffi` под Chrome.
2. Выставляет **куку региона** `yandex_gid` со значением `yandex_market_id`
   (`_apply_yandex_region`) — так Маркет покажет цены и доставку нужного города.
3. Заходит на главную `market.yandex.ru` — это «разогрев»: имитация того, что
   пользователь сначала открыл сайт, а уже потом ищет.

> **Кука (cookie)** — маленькая пометка, которую сайт хранит про посетителя.
> Здесь ею мы сообщаем Маркету выбранный регион.

### Шаг 3. Пагинация с «умной остановкой»

Функция `_collect_paginated_products` листает страницы поиска (по умолчанию до
`ym_search_max_pages = 3`), между страницами — пауза `PAGE_DELAY_SEC = 0.8` сек.
Листание прекращается досрочно, если:

- страница пустая или это **блокировка/капча** (`_is_blocked`);
- на странице **не нашлось** разбираемых товаров;
- на странице **не добавилось ни одного нового** товара (всё мусор или дубли) —
  значит, дальше листать смысла нет.

## 5. Как из HTML достаются товары

Это сердце файла — функция `_parse_search_html`. Она проходит по карточкам
товаров на странице (`<article>`) и из каждой достаёт поля по `data-auto`-меткам:

| Поле `Product` | Откуда на странице |
|----------------|--------------------|
| `title` (название) | `[data-auto="snippet-title"]`, чистится `_clean_title_text` |
| `price` (цена, в копейках) | `[data-auto="snippet-price-current"]` → `_parse_price_rub` |
| `product_url` (ссылка) | ссылка на `/product/` или `/card/` |
| `image_url` (картинка) | первый `<img>` карточки |
| `rating`, `reviews_count` | блок `[data-auto="reviews"]` → `_parse_rating`, `_parse_reviews` |
| `characteristics` | вытаскиваются **из самого названия** (`_extract_characteristics`) |

Текст в вёрстке «человеческий» («4.8 (213)», «1 234 ₽»), поэтому числа из него
выковыривают регулярные выражения. Например, цена «1 234 ₽» → убираем всё, кроме
цифр → `1234` → переводим в копейки (`× 100`).

Любопытная деталь: на странице поиска у товара мало характеристик, поэтому
**часть характеристик угадывается прямо из названия**: память («256 ГБ»), цвет
(«чёрный»), вариант комплектации (текст после первой запятой).

## 6. Фильтрация: мусор и дубликаты

Не всё, что вернул поиск, нам нужно. Каждый товар проходит «сортировку»
(`_classify_listing`) с одним из трёх вердиктов:

- **`duplicate` (дубликат)** — такой URL уже видели, **или** название слишком
  похоже на уже принятое. Похожесть считается двумя способами: точное совпадение
  после нормализации (`_normalize_title`) или коэффициент схожести ≥ 0.93 через
  `SequenceMatcher`.
- **`garbage` (мусор)** — `_is_garbage_listing`: либо в названии **нет ни одного
  значимого слова из запроса**, либо это аксессуар (чехол, стекло, плёнка,
  кабель, зарядка, наушники…), хотя сам запрос не про аксессуары. Так по запросу
  «телефон» отсекаются «чехол для телефона» и «защитное стекло».
- **`accepted` (принято)** — добавляем в результат.

> ⚠️ В коде это помечено как **временная эвристика** (`Stub heuristics — replace
> with ML/ranking later`): набор стоп-слов и порогов подобран вручную, и в
> будущем его планируют заменить нормальным ML-ранжированием.

---

## 7. Обогащение карточек (enrichment)

После фильтрации у нас есть список товаров, но с **бедным описанием** (то, что
было в сниппете поиска). Чтобы дополнить их, скрапер делает **второй заход**:
открывает страницу каждого товара и дочитывает детали (`_enrich_product`):

- `_parse_card_prose` — текстовое описание товара;
- `_parse_card_specs` — таблицу характеристик;
- собирает красивое итоговое описание (`_build_description`) и повышает
  «уверенность» товара (`confidence`) с 0.9 до 0.95.

Карточек может быть много, а каждая — это отдельный сетевой запрос. Поэтому
обогащение идёт **параллельно в 4 потока** (`ThreadPoolExecutor`,
`CARD_FETCH_WORKERS = 4`) — это функция `_enrich_products`. Если какая-то карточка
не открылась или заблокирована — товар остаётся с тем, что было, и поиск не
ломается.

> **`confidence`** — наша внутренняя оценка «насколько данным о товаре можно
> доверять». Обогащённая из карточки запись надёжнее, чем собранная только из
> сниппета, — отсюда 0.95 против 0.9.

## 8. Запасной план: Playwright

Если `curl_cffi` ничего не вернул или упал (например, Яндекс показал капчу),
`search` переключается на `_fetch_with_playwright` — **настоящий браузер
Chromium**.

> **Playwright** — инструмент, который запускает реальный браузер «без рук» и
> позволяет программно открывать страницы. Тяжелее и медленнее обычных запросов,
> зато выглядит максимально как живой пользователь и чаще проходит антибот.

В этом режиме браузер прячет признаки автоматизации (отключает флаг
`navigator.webdriver`, флаг `AutomationControlled`), выставляет ту же куку
региона и листает те же страницы. Дальше — **тот же самый** парсинг
(`_parse_search_html`), фильтрация и обогащение, что и в основном пути: код
переиспользуется.

Если Playwright не установлен — путь просто пропускается (без падения).

## 9. Защита от сбоев и блокировок

Как и у WB-скрапера, философия — **деградировать, а не падать**:

1. **Кэш** — большинство повторных запросов не доходит до Маркета.
2. **Разогрев + кука региона + Chrome-отпечаток** — чтобы выглядеть как человек.
3. **Паузы между страницами** (0.8 сек) — чтобы не частить.
4. **Детект блокировки** (`_is_blocked`) — ловит SmartCaptcha, текст «подтвердите,
   что запросы отправляли вы» и короткие страницы с кодом 403; в этом случае
   листание прекращается.
5. **Двухуровневый фоллбэк** — `curl_cffi` → Playwright.
6. **Graceful degradation** — при любой ошибке отдаём `[]` и пишем понятный текст
   в `last_error` (механизм `BaseScraper`), общий поиск по другим площадкам
   продолжается.

## 10. Асинхронность: почему вызовы обёрнуты в `asyncio.to_thread`

`curl_cffi`, Redis и обогащение в потоках — **синхронные** (блокирующие)
операции. Само приложение (FastAPI) асинхронное и не должно «замирать» на время
сетевых вызовов. Поэтому блокирующая работа запускается через
`await asyncio.to_thread(...)` — event loop остаётся свободным и может
параллельно скрапить другие площадки. Playwright здесь изначально асинхронный
(`async_playwright`).

---

## 11. Что можно увидеть в логах

- `Yandex Market cache hit` — ответ взят из кэша.
- `Yandex Market page N blocked or empty` — капча/блокировка, листание остановлено.
- `Yandex Market page=N accepted=.. duplicates=.. garbage=..` — статистика
  фильтрации по странице (уровень DEBUG).
- `Yandex Market stop at page=N: no new products` — досрочная остановка пагинации.
- `Failed to enrich Yandex Market product` — не удалось обогатить карточку.
- `curl_cffi: ...` / `Playwright: ...` в `last_error` — какой путь и почему упал.

## 12. Главные ограничения текущей версии

1. **Фильтрация — временная эвристика** (стоп-слова + пороги), а не ML;
   возможны и ложные срабатывания, и пропуски.
2. **Хрупкость к вёрстке** — скрапер завязан на `data-auto`-метки Маркета; если
   они изменятся, парсинг придётся править.
3. **Дороже, чем WB** — много запросов (страницы + карточки), плюс возможный
   запуск браузера.
4. **Нужен подходящий IP** — иначе капча/403; для этого и существует фоллбэк на
   Playwright.
