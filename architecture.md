# Архитектура решения: агрегатор цен с маркетплейсов

Полностью бесплатный стек. Сервис собирает цены с Wildberries, Ozon, Яндекс Маркета и одного динамического (нефиксированного) источника из Рунета, группирует результаты, исправляет опечатки, понимает синонимы и ранжирует выдачу по релевантности.

---

## Принципы, на которых строится система

1. **Кеш — главная защита.** При работе ничего не идёт "вживую" без необходимости. Это решает три проблемы сразу: скорость, блокировки, лимиты внешних сервисов.
2. **Дешёвые методы первыми, дорогие — fallback.** SymSpell перед LLM. Регулярки перед vision-моделью. Это снижает нагрузку и держит latency в норме.
3. **WB через JSON API — опора надёжности.** Самый стабильный канал, который держит сервис даже когда остальные источники тормозят.
4. **CV-модель только для 4-го источника.** Там она реально незаменима — для произвольного сайта парсер написать нельзя.
5. **Параллелизм везде.** Четыре источника опрашиваются одновременно через `asyncio.gather`.
6. **Деградация, а не падение.** Если Ozon молчит — показываем остальное и помечаем "источник недоступен".

> ⚠️ **Главная архитектурная проблема:** соблазн "сделать всё через LLM/Vision" — это медленно, дорого по ресурсам и нестабильно. Каскадная архитектура обязательна, иначе на демо запрос будет обрабатываться 30+ секунд.

## Архитектурная схема

```
┌──────────────────────────────────────────────────────────────────┐
│              FRONTEND (React + Vite + Tailwind)                  │
│  Поисковая строка → результаты, сгруппированные по источникам    │
│  Карточка: фото, название, цена, ссылка, характеристики          │
│  Бейджи: "исправлено X→Y", "синонимы: ...", релевантность        │
└──────────────────────────────────┬───────────────────────────────┘
                                   │ HTTP REST
                                   ▼
┌──────────────────────────────────────────────────────────────────┐
│                  API GATEWAY (FastAPI, async)                    │
│  POST /search { query }                                          │
│  POST /search/stream  (SSE для прогресса по источникам)          │
└──────────────────────────────────┬───────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────┐
│                       QUERY PROCESSOR                            │
│  Typo correction (SymSpell) → Synonym expansion (WordNet+LLM)    │
│  → Cache lookup (Redis, TTL 6h)                                  │
└──────────────────────────────────┬───────────────────────────────┘
                                   │ MISS
                                   ▼
┌──────────────────────────────────────────────────────────────────┐
│            ORCHESTRATOR (asyncio.gather, timeout 8s)             │
└──┬───────────┬───────────┬────────────────┬──────────────────────┘
   ▼           ▼           ▼                ▼
┌────────┐ ┌────────┐ ┌────────────┐ ┌────────────────────────┐
│  WB    │ │  ЯМ    │ │   Ozon     │ │  4-й источник          │
│ JSON   │ │curl_cffi│ │ Playwright│ │ SearXNG → top-3 сайтов │
│ API    │ │chrome120│ │ + stealth │ │ → Schema.org → Vision  │
└───┬────┘ └───┬────┘ └─────┬──────┘ └────────────┬───────────┘
    └──────────┴────────────┴─────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│  NORMALIZER → VALIDATOR (rubert-tiny2) → RANKER → CACHE WRITER   │
└──────────────────────────────────────────────────────────────────┘
```

## Технологический стек

| Слой | Технология | Комментарий |
|---|---|---|
| Frontend | React + Vite + Tailwind + shadcn/ui | Быстрая красивая верстка |
| Backend | FastAPI + Uvicorn (async) | Нужен async для параллельного скрапинга |
| HTTP-клиент | `curl_cffi` (chrome120 impersonation) | Обходит TLS-fingerprint в одну строку |
| Браузер | Playwright + `playwright-stealth` | Только для Ozon |
| Прокси-ротация | 3–5 Cloudflare Workers (free tier) | 100k запросов/день каждый, бесплатно |
| Метапоиск | SearXNG в Docker (self-hosted) | Агрегирует Bing/Google/Yandex без ключей |
| Извлечение из HTML | `trafilatura` + `selectolax` + Schema.org JSON-LD | Schema.org — золото, есть у 70% магазинов |
| Опечатки | SymSpellPy + словарь русского (1.5М слов) | Локально, ~5 мс на запрос |
| Синонимы | WordNet (rusyn) + Ollama Qwen2.5-7B fallback | LLM только при необходимости |
| Эмбеддинги текста | `cointegrated/rubert-tiny2` | 45 МБ, CPU, русский |
| Vision (4-й источник) | Moondream2 локально / OpenRouter free | CV-фишка проекта |
| Матчинг товаров | CLIP `sentence-transformers/clip-ViT-B-32` | "Это один и тот же товар?" между источниками |
| Кеш | Redis в Docker | TTL 6 часов |
| Очередь | Celery + Redis | Для прогрева кеша по расписанию |
| Оркестрация | Docker Compose | Одна команда `up` |

> ⚠️ **Проблема:** Ollama на CPU генерирует ~5–10 токенов/сек. Запрос синонимов = ~3 секунды. Решение — кешировать ответы LLM на диск и вызывать только когда дешёвые методы не справились.

## Компоненты в деталях

### 1. Query Processor — нормализация запроса

Каскад обработки от дешёвого к дорогому:

```
вход → чистка whitespace
     → SymSpell (5 мс)
     → если нашлись редкие слова без коррекции → Ollama (2 сек)
     → WordNet синонимы (10 мс)
     → если категория неочевидна → Ollama генерация вариантов (3 сек)
     → выход: {original, corrected, synonyms[]}
```

**Зачем каскад:** 90% запросов обрабатываются за 15 мс без вызова LLM. Только редкие сложные кейсы поднимают latency.

> ⚠️ **Проблема:** SymSpell с большим словарём (1.5М слов) при инициализации жрёт 200 МБ памяти и грузится 3–5 секунд при старте. Решение — lazy load + урезанный словарь до 100k самых частотных русских слов (хватает для 99% опечаток).

### 2. Источники данных

#### 2.1 Wildberries — основа надёжности

Прямой JSON API без прокси:
- `https://search.wb.ru/exactmatch/ru/common/v5/search?query=...` — поиск
- `https://card.wb.ru/cards/v1/detail?nm=...` — карточка с характеристиками
- Картинки по шаблону URL из ID товара

**Не требует:** прокси, браузера, авторизации, капч.

> ⚠️ **Проблема:** WB неофициально, без гарантий стабильности структуры. На прошлой неделе могло быть поле `priceU`, сейчас `sizes[0].price.total`. Решение — защитный парсинг через try/except и дефолты на каждое поле + проверка работоспособности за день до защиты.

---

#### 2.2 Яндекс Маркет — через curl_cffi

```
curl_cffi(impersonate="chrome120") + реалистичные заголовки
+ Cloudflare Worker как прокси
+ selectolax для парсинга HTML
+ fallback: если 200 OK но выдача пуста → Playwright
```

> ⚠️ **Проблемы ЯМ:**
> - Может вернуть страницу-заглушку без данных при отсутствии правильных cookies
> - SmartCaptcha срабатывает на серверных IP
> - Иногда отдаёт A/B-варианты с разной разметкой
>
> **Митигация:** прогрев сессии (зайти на главную → подождать → искать), использование Cloudflare Worker как промежуточного звена с разными IP, кеш на 6 часов.

---

#### 2.3 Ozon — самый проблемный источник

```
Playwright headless + playwright-stealth
+ persistent context (один Chromium на все запросы)
+ Cloudflare Worker для смены IP
+ блокировка картинок/шрифтов/CSS через route.abort (-70% времени)
+ прогрев: главная → задержка → поиск
```

> ⚠️ **Проблемы Ozon — самая большая боль проекта:**
> - Серьёзный антибот (Akamai + собственные эвристики)
> - Капча/блок при частых запросах с одного IP
> - JS-рендеринг обязателен
> - Playwright тяжёлый (~300 МБ RAM на инстанс)
> - Без резидентных прокси (которые платные) обход неполный
>
> **Митигация:** агрессивный кеш + прогрев перед демо + резервный режим со снимками JSON-ответов на случай блокировки. На презентации запросы должны идти из кеша, иначе риск провала.

---

#### 2.4 Четвёртый источник — динамический

Главная техническая фишка проекта. Логика трёхуровневая:

**Шаг 1.** SearXNG (self-hosted метапоисковик в Docker) выполняет поиск:
```
"{query} купить цена -site:market.yandex.ru -site:ozon.ru -site:wildberries.ru"
```
Получаем top-10 ссылок с разных доменов из Рунета.

**Шаг 2.** Выбираем top-3 уникальных доменов. Для каждого пробуем извлечь данные каскадом:

1. **Schema.org JSON-LD** в `<script type="application/ld+json">`. Есть у 70% нормальных магазинов. Содержит цену, название, картинку, бренд в структурированном виде. **Это золото.**
2. **Трафилатура + регулярки.** Если JSON-LD нет — извлекаем основной контент, ищем цену регулярками `\d[\d\s]*₽`.
3. **Vision-модель** (Moondream2 или OpenRouter free). Если HTML не разобрался — делаем скриншот через Playwright и просим модель извлечь данные.

**Почему сильно:**
- 4-й источник реально динамический — на разные запросы возвращаются разные магазины
- Каскад от дешёвого к дорогому: 70% случаев обрабатываются регулярками за 100 мс, vision только на сложных
- Vision как настоящая ML-фишка для презентации

> ⚠️ **Проблемы 4-го источника:**
> - SearXNG публичные инстансы могут лечь → запускаем свой в Docker
> - DuckDuckGo HTML тоже даёт капчи при частых запросах → SearXNG агрегирует несколько движков, это устойчивее
> - Vision-модель на CPU работает 20–30 сек → используется только в крайнем случае + кешируется
> - Регулярки ловят цену доставки/зачёркнутую цену → отсев через Schema.org приоритетно или проверка через эмбеддинги контекста
> - У случайных сайтов могут быть капчи, которые мы не пробьём → пропускаем такой домен, берём следующий из выдачи

### 3. Слой обхода блокировок — многоуровневая защита

#### Уровень 1: Базовая гигиена (всегда применяется)
- `curl_cffi` с `impersonate="chrome120"` — обход TLS-fingerprint одной строкой
- Реалистичные заголовки (`Sec-Fetch-*`, правильный порядок)
- Случайные задержки 1.5–4 сек между запросами к одному домену
- Exponential backoff на 429: 2, 4, 8, 16 секунд

#### Уровень 2: Ротация IP (бесплатно через Cloudflare Workers)
3–5 воркеров в разных Cloudflare аккаунтах. Каждый — прокси-шлюз, переадресует запросы. Round-robin между ними в коде. У Workers разнообразный пул IP, который не палится как датацентр.

#### Уровень 3: Stealth-браузер (для Ozon)
- Playwright + `playwright-stealth` (убирает `navigator.webdriver`, эмулирует canvas/WebGL)
- Persistent context — переиспользуем один Chromium
- Эмуляция движений мыши перед кликами

#### Уровень 4: Капчи (заготовка, не активирована)
- Детектор капчи в pipeline (по тексту/заголовкам/статусу)
- При обнаружении: смена IP + сброс cookies + retry
- TrOCR локально для текстовых капч (код готов, не используется на демо)
- В слайдах: "для production интегрируется 2captcha"

#### Уровень 5: Кеш как защита
- Redis с TTL 6 часов
- Ключ = нормализованный query + источник
- **Прогрев перед демо** — за час прогнать показательные запросы

> ⚠️ **Главная проблема обхода блокировок без денег:** бесплатные ресидентные прокси не существуют. Cloudflare Workers — компромисс, но не идеален для Ozon. Поэтому **кеш и прогрев** — не оптимизация, а критическая часть архитектуры.

### 4. Normalizer + Validator

Все источники приводятся к единой модели `Product`:

```python
class Product:
    source: Literal["wb", "ozon", "yandex_market", "other"]
    source_domain: str           # "wildberries.ru" или "dns-shop.ru"
    title: str
    price: int                   # в копейках, избегаем float
    currency: str = "RUB"
    image_url: str
    product_url: str
    characteristics: dict[str, str]
    rating: float | None
    reviews_count: int | None
    relevance_score: float       # cosine similarity с query
    confidence: float            # уверенность парсера (0..1)
```

**Валидация через эмбеддинги:** считаем cosine similarity между запросом и названием товара. Порог 0.5 — отсекает мусор (чехлы при поиске телефона).

> ⚠️ **Проблема:** на запрос "iPhone 15" Ozon охотно вернёт чехлы для iPhone 15. Без валидатора это позор на сцене. С валидатором — нужно подобрать пороги: слишком строгий → теряем релевантное, слишком слабый → пропускаем мусор. Калибровать на 20 размеченных вручную запросах.

---

### 5. Ranker — финальное ранжирование

```
эмбеддинги запроса и всех названий батчем (50 мс на 100 товаров)
→ cosine similarity → relevance_score у каждого
→ группировка по источникам
→ сортировка внутри группы по score
→ агрегаты: min/median/max цена, количество
```

> ⚠️ **Проблема:** `rubert-tiny2` на CPU обрабатывает ~50 мс на текст по одному. Решение — батчевый инференс через `model.encode([titles])` за раз — даёт 10× ускорение.

### 7. Frontend — что показываем пользователю

- Поле поиска с автокомплитом
- Под полем — бейджи: "исправлено: айфно → айфон", "также искали: iphone 15"
- Четыре блока групп с иконками источников и счётчиками

## Деплой: Docker Compose

```yaml
services:
  api:           # FastAPI backend
  frontend:      # React build
  redis:         # Кеш
  searxng:       # Метапоиск для 4-го источника
  ollama:        # LLM локально
  playwright:    # Браузер в отдельном контейнере
```

Одна команда `docker-compose up` — всё работает.

> ⚠️ **Проблема:** на слабом ноутбуке всё одновременно — это 6+ ГБ RAM (Ollama 5 ГБ + Playwright 0.5 ГБ + Vision-модель 4 ГБ + остальное). Решение — на демо использовать OpenRouter free tier для vision и Ollama выключить, оставив SymSpell+WordNet.

## Порядок реализации

### Этап 1: Инфраструктура
- Поднять Docker Compose (Redis + SearXNG + Ollama)
- Скелет FastAPI с `/search` endpoint
- Скелет React с полем поиска
- OpenAPI-схема — фронт генерирует типы автоматически

### Этап 2: Wildberries как первый рабочий канал
- Парсер через `search.wb.ru` API
- Модель `Product`, нормализация полей
- Подключение Redis кеша
- Первый end-to-end сценарий: запрос → WB → карточка на фронте

> ⚠️ **Точка риска:** на этом этапе важно не уйти в перфекционизм. WB работает за 2–3 часа, дальше идёт к Ozon. Если завязнуть на полировке WB — не успеть остальное.

### Этап 3: Яндекс Маркет и Ozon
- ЯМ через `curl_cffi` + selectolax
- Ozon через Playwright stealth
- Cloudflare Worker для прокси (хотя бы один пока)
- Тестирование на 3–4 запросах

> ⚠️ **Точка риска:** Ozon может не пойти. План Б — оставить Ozon только в "режиме кеша" с заранее собранными ответами, в коде честно описать, как это работает в проде.

### Этап 4: Query Processor
- SymSpell + русский словарь (урезанный до 100k слов)
- WordNet синонимы
- Подключение Ollama как fallback
- Тестирование на 5 кейсах с опечатками

### Этап 5: Четвёртый источник
- SearXNG в Docker, конфиг engines
- Schema.org JSON-LD extractor
- Trafilatura + регулярки для остального
- Тесты на 3–4 случайных магазинах Рунета

> ⚠️ **Точка риска:** магазины могут оказаться сильно разными. Если регулярки ловят мусор — vision-модель спасает, но это медленно. Решение — фиксированный whitelist 5–10 крупных магазинов на демо, но **код работает на любом**, что и показываем жюри.

### Этап 6: ML-компоненты
- `rubert-tiny2` для ранжирования и валидации (батчевый инференс)
- Vision-модель (Moondream2 локально или OpenRouter free) для сложных случаев
- CLIP для матчинга одинаковых товаров между источниками (бонус, если успеваем)

### Этап 7: Frontend полировка
- shadcn/ui карточки
- Группировка по источникам с бейджами
- Индикатор обработки (исправлено, синонимы)
- Фильтры по цене и источнику

### Этап 8: Тесты и подготовка
- Прогон 10–15 тестовых кейсов разных категорий
- Калибровка порогов валидации
- Прогрев кеша перед демо
- Запись резервного видео

### Этап 9: Презентация
- Слайды: проблема → архитектура → фишки → масштабирование → команда
- Метрика качества: precision@5 на 20 размеченных запросах
- Репетиция timing'а

## Что отличает решение от типовых

Большинство команд на таком хакатоне делают: "три скрапера → веб-поиск как 4-й → React-фронт".

Наши отличия:

1. **Не один путь — каскады.** На каждом этапе несколько стратегий с fallback.
2. **CV не для галочки, а в нужном месте** — 4-й источник, где регулярки бессильны.
3. **Архитектура думает о проде**, а не только о демо: кеш, ротация IP, очередь обновлений, деградация вместо падения.
4. **Прозрачность для пользователя** — он видит, как система его понимает (исправления, синонимы, релевантность).
5. **Семантическое ранжирование** на русскоязычной модели — карточки сортируются осмысленно, а не как в API.
6. **CLIP-матчинг одного товара между источниками** — мало кто сделает за 2 дня, при наличии — сильное преимущество.
7. **Реально бесплатно по факту**, не "потом купим". Каждое решение работает на free tier.

## Главный честный риск

**Ozon — основная точка боли всего проекта.** Без платных резидентных прокси полностью надёжного скрапинга Ozon на хакатоне не сделать. Стратегия: кеш + один Cloudflare Worker + stealth + ручной прогрев перед демо + готовность объяснить жюри, как это решается в production (партнёрский API или платные прокси). Этой честности обычно достаточно — жюри ценят понимание ограничений больше, чем магическое решение всех проблем.
